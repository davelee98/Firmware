01 Execution model

Both targets are Arduino-on-FreeRTOS, and on both, loop() is a task among others rather than the whole program. The task rank differs, and it is the single most important asymmetry in this document.

Since the Phase 3 transport unification, the callback contract is symmetric on both targets: a BLE stack callback may do exactly two things — copy bytes into the RX ring and set a flag. Everything else (command dispatch, zlib inflate, EPD SPI streaming, notify, connect/disconnect application work, the PHY/DLE request) runs on the loop task. ble_transport_nrf.cpp:118-124, ble_transport_esp32.cpp:79-81

Consequence. There is no watchdog backstop on either target. Every bound listed in this document is a bound the code imposes on itself; if one is exceeded the device stays in that state until power is cycled. On ESP32 every environment defines -DCONFIG_FREERTOS_WATCHDOG_TIMEOUT_S=120 in build_flags, but the loop task's own WDT subscription is separately gated on loopTaskWDTEnabled, which is false at boot and never set.
nRF starvation is structural. Because the loop task sits below both the callback task (2) and the BLE/SOC tasks (3), sustained BLE traffic can starve loop() with no single blocking call responsible. The heartbeat exists precisely to tell that apart from a blocked loop: a beat arriving with loops in the thousands is a healthy idle link, a beat with loops near zero is a starved loop, no beat at all is a blocked one. diagnostics.cpp:85-124

04 idleDelay() — the cooperative wait

The only sanctioned way for loop() to wait. It is called only from loop(), never from a command handler — which is what makes its RX rule safe to state as a hard invariant. main.cpp:725-751

Serviced during the wait

  • ble.tick() — nRF only
  • processButtonEvents()
  • processTouchInput()
  • processLedFlash()
  • epdSessionTick() — keep-alive still expires
  • buzzerService()
  • serviceBleTx() — safe, it only notifies
  • Early return the moment bleRxQueuePending()

Not serviced

  • serviceBleEvents() — connect/disconnect wait for the next pass
  • serviceBleRx() — deliberate: dispatching here would make command handlers reentrant and corrupt multi-frame transfer state
  • serviceBleDisconnectCleanup() / serviceBleAdvertisingRestart()
  • handleWiFiServer() — LAN is frozen for the wait
  • The two 15-minute session watchdogs
  • diagHeartbeat() / periodic updatemsdata()

The wait is chunked at 100 ms, so command latency is capped at one chunk rather than the caller's full delay — which is what makes nRF's move to loop-side dispatch viable, given its idle waits are 500 ms and up.

05 ESP32 power policy — the two hooks

Deep sleep, the wake-advertising window and the activity poller are ESP32-only capabilities, hooked rather than merged into the shared body.

pollActivity() — one point of activity detection

Rather than have every producer stamp a timestamp, the poller samples state the producers already mutate and treats any change since the previous pass as activity: RX/TX queue heads, connection count, live LAN session, the 11-byte dynamicreturndata block (buttons and touch land here), the pending advertising-restart flag, and any pending queue work. It runs at the top of the pass so an event raised during the previous pass always lands before this pass decides to sleep. main.cpp:333-380

A connected link is activity in itself. connCount > 0 stamps lastActivityMs on every pass, so a client that connects and does nothing holds the device awake indefinitely — by design, not by omission.

The wake-advertising window

On a deep-sleep wake, platformLoopPrologue() claims the entire pass — steps 7 through 19 of the main body never run — and re-enters on a 50 ms idleDelay() cadence until one of three things happens: a client connects (→ fullSetupAfterConnection(), window closed), the quiet window elapses with no min-wake hold (→ enterDeepSleep()), or work keeps re-arming the window. The window is measured from last activity, not from window start, so a client that connects and drops re-arms the full window. main.cpp:546-589

Inside the window the branch still calls serviceBleDisconnectCleanup() and serviceBleAdvertisingRestart() before the timeout test, because a connect-and-drop entirely inside one poll gap would otherwise leave the radio dark for the rest of the window.

The RX ring depth is derived, not chosen: it must absorb a full unacknowledged PIPE window plus the END frame that sits outside the window's sequence space, during a stall of up to 60 s. Hence PIPE_MAX_W + 2 slots for PIPE_MAX_W + 1 usable.

Command dispatch

imageDataWritten() is the single dispatcher for both transports. AUTHENTICATE (0x0050) and FIRMWARE_VERSION (0x0043) are handled ahead of the encryption gate as the handshake; a frame arriving over TLS-PSK LAN bypasses the app-layer CCM envelope entirely; everything else must decrypt or is rejected. The switch then covers reboot, config read/write/chunk/clear, MSD read, DFU, power-off, deep-sleep, the legacy direct-write trio 0x0070–0x0072, LED activate/stop, partial-write start 0x0076, buzzer, and the PIPE trio 0x0080–0x0082. communication.cpp:541-704

Responses

Every response goes through sendResponse(), which applies the CCM envelope when authenticated (skipping the handshake opcodes, FE/FF statuses and TLS-origin frames), logs one TX line with the pre-enqueue ring depth, and routes to the origin transport only — BLE ring or LAN frame, never both. communication.cpp:211-276 Handlers that generate many responses in one call flush the ring themselves: handleReadConfig() calls serviceBleTx() between chunks, because the loop task is the ring's only drainer and cannot run until the handler returns. communication.cpp:388-397

Link tuning

Both targets request 2 Mbps PHY and 251-octet DLE when the connect event is consumed — from the loop task, not the callback, since those are stack calls. nRF logs the link twice (baseline at connect, negotiated ~2.5 s later via a one-shot timer); ESP32 logs on the PHY-update and MTU-change callbacks instead. ble_transport_nrf.cpp:270-294, ble_transport_esp32.cpp:311-327
